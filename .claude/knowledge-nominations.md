# Knowledge Nominations

Candidate learnings from agents and sessions. The auditor reviews these

## Pending Nominations

- [043026] /wrap-up: **Use the type system to validate input where possible.** `s.parse::<u64>()` rejects negatives for free. Choosing `u64` over `i64` for `Incr.by` shifted the "no negative amounts" rule from a runtime check into a parse-time error message — fewer code paths, clearer errors, no manual branch needed. | Evidence: agent inference 043026 — applied during `Incr`/`Decr` field-type decision; user confirmed the semantic preference ("incr by negative is weird"). | Status: DEFERRED — one confirmed application; promote after a second instance surfaces.

- [050126] /wrap-up: **`?` propagates from the current function/closure only — it cannot escape closure boundaries.** Putting `?` inside an `and_then(|s| ...)` closure tries to early-return from the closure, not the enclosing function. The closure's return type (`Option<U>`) and the outer function's return type (`Result<_, _>`) are independent. Workaround: lift the fallible step out of the closure into the function body (use `match parts.next() { Some(s) => s.parse()?, None => default, }`). | Evidence: empirical 050126 — compile error E0277 on `parts.next().and_then(|s| s.parse::<u64>()?).unwrap_or(1)` during `incr` arm work. | Status: PROMOTED 050126.

- [050126] /wrap-up: **Local type inference can fail at closure boundaries when generic methods meet integer-literal ambiguity.** `s.parse().map_err(|e| e.to_string())` won't compile when the eventual target is `u64` — because `1` in a sibling `match` arm keeps `T` as `{integer}` until later, and `T::Err` can't be resolved at the closure body. Fix: pin the target type at the `parse()` site with turbofish (`s.parse::<u64>()`). General rule: when inference stalls with "type annotations needed" inside a closure, annotate the generic call upstream, not the closure parameter. | Evidence: empirical 050126 — compile error E0282 on `s.parse().map_err(|e| ParseError::InvalidAmount { reason: e.to_string(), ... })`. | Status: PROMOTED 050126.

- [050126] /wrap-up: **`From<E1> for E2` cannot capture calling-scope context — it only sees the source error.** When you need an error variant to carry context that's only available at the call site (e.g. the bad input the user typed), drop the `From` impl and use `.map_err(|e| Variant { input: s.to_string(), reason: e.to_string() })?` at the site. Trade auto-`?`-via-`From` for richer error data. | Evidence: agent inference 050126 — applied during `InvalidAmount { input, reason }` design after recognizing `From<ParseIntError>` could only access the `ParseIntError`, not the original `&str`. | Status: PROMOTED 050126.

- [050126] /wrap-up: **Asymmetric error variants for asymmetric data sources is idiomatic Rust.** `&'static str` for hardcoded labels you control at the call site (zero alloc, no lifetime parameter), `String` for user input/runtime data, struct variant `{ input: String, reason: String }` when both pieces add value. The mix in one enum is normal and signals the variant's data shape. | Evidence: agent inference 050126 — applied across `Empty` (unit) / `MissingArg(&'static str)` / `UnknownCommand(String)` / `InvalidAmount { input, reason }` in `cmd::ParseError`. | Status: PROMOTED 050126.

- [050126] /wrap-up: **Patterns are a separate language from expressions** — no function calls, no method calls, no construction (`String::from(...)` etc.). To assert against a complex value inside a match arm, either use a guard (`pattern if expr`) or bind first and assert second. The "bind then assert" form gives the best test failure messages because `assert_eq!` produces a side-by-side diff; the guard form just produces a generic "didn't match" panic. | Evidence: empirical 050126 — `Err(ParseError::UnknownCommand(String::from("foo")))` pattern rejected; replaced with `Err(ParseError::UnknownCommand(s)) => assert_eq!(s, "foo")`. | Status: PROMOTED 050126.

- [050226] /wrap-up: **`#[expect(lint, reason = "...")]` is the modern alternative to `#[allow(lint)]`.** It silences the lint AND requires the lint to be firing — when the lint stops firing, the `expect` itself warns ("expectation unfulfilled"), forcing you to remove the attribute. Self-cleaning, no manual housekeeping. Use it for *temporary* lint silences (work-in-progress fields, deferred impls) where you know the suppression should expire. Stable since Rust 1.81. | Evidence: agent inference 050226 — used on `InMemoryStorage.data` field at storage.rs stopping point A; will warn out the moment point B's impl methods touch the field. | Status: PROMOTED 050626.

- [050226] /wrap-up: **`to_ascii_lowercase()` over `to_lowercase()` for ASCII-only matching.** `to_lowercase()` runs the full Unicode case-folding algorithm — locale-independent but costly, and surprising (e.g. `İ` lowercases to `i` + combining-dot, two characters from one). For ASCII verbs / keys / fixed identifiers, `to_ascii_lowercase()` is a byte-level transform: faster, length-preserving, and *honest* about intent (signals "I only deal with ASCII here"). Both allocate a new `String`. | Evidence: empirical 050226 — applied during `cmd::FromStr` case-insensitivity work; `to_lowercase()` was working but doing more than needed. | Status: PENDING.

- [050226] /wrap-up: **Compiler errors on structural issues (missing brace, missing `;`, unclosed paren) often point to *the next syntactically wrong thing*, not the actual missing element.** When the error site looks correct, walk *up* the file looking for structural mismatch — the parser kept consuming tokens until something didn't fit, then reported there. Heuristic: trust syntax that mirrors working code in the same file; if `Ok(())` looks right by symmetry to other `Ok(...)` sites, the bug is elsewhere. | Evidence: empirical 050226 — user "fixed" `Ok(())` → `Ok()` thinking the paren looked weird, when the actual error was a missing closing `}` further down. | Status: PENDING.

- [050226] /wrap-up: **Rust is expression-oriented; `;` is a value-discarder, not a statement terminator.** The last expression in a block — *without trailing `;`* — is the block's value. Function bodies follow this rule (implicit return = trailing expression). Adding `;` to the final `match { ... }` of a function turns the match into a statement, the function returns `()`, and you get *"expected T, found ()"* errors. Diagnostic heuristic: that error message → walk to the bottom of the function, look for an offending `;`. | Evidence: empirical 050226 — surfaced during the `expect_done` helper construction; user noticed the absence of `;` after match was "very strange" coming from C-family languages. | Status: PENDING.

- [050226] /wrap-up: **Avoid making decisions where a refactor is already certain.** When weighing options, classify the eventual refactor as *certain* (forced by the milestone arc / known constraint) or *possible* (could happen, depends on later choices). For certain refactors, pick the option that absorbs the cost upfront — short-term simplicity isn't worth eventual churn. The "you'll learn from a future refactor" argument applies only to *possible* refactors. | Evidence: agent inference 050226 + user override 050226 — applied when picking `Option<String>` over `Option<&str>` for `Storage::read`. M6 replication forces owned for sure. User explicit: "not a fan of making decisions where we already know a refactor is coming for sure." | Status: PENDING.

- [050226] /wrap-up: **ADR rigor scales with stakes.** Not every ADR earns equal weight. Low-stakes decisions (where either option would have shipped) get a thin recording — Context + Decision is enough. High-stakes decisions (where the choice constrains the milestone arc) get a thicker alternatives section explaining *why* the rejection mattered. Forcing equal rigor on every ADR inflates the low-stakes ones and dilutes the high-stakes ones. | Evidence: user override 050226 — explicit framing during M1 ADR pass: "for these two specifically the choices are not critical so either options we go with is fine; we just went this way and the ADR states that." | Status: PENDING.

- [050426] /wrap-up: **Line coverage % can be dragged down by test-only defensive code.** A `match` arm like `other => panic!("got {other:?}")` in tests is good practice — produces useful diagnostics on assertion failure — but coverage tools count it as 0% covered because it only executes when the test *fails*. Production code coverage is what matters; report the number with that caveat. Don't refactor tests to chase the coverage metric; the bind-then-assert idiom (already in knowledge-base) is worth keeping. Possible mitigation if the metric matters: collapse simple-Err tests to `assert_eq!(result, Err(ParseError::Variant("expected")))` directly (works because errors derive PartialEq) — but mixing styles inside one test module is worse than uniform style, and tests that need partial-match (e.g. `reason.contains("invalid digit")`) can't collapse anyway. | Evidence: empirical 050426 — `cargo llvm-cov` reported cmd.rs at 95.24% line coverage; HTML output showed all 14 missed lines were `panic!` arms in test bodies. | Status: PROMOTED 050426.

- [050426] /wrap-up: **`cargo clippy` does not subsume `cargo fmt`; both must run locally to match CI.** Clippy is a *lint* check (idioms, correctness suggestions); rustfmt is a *layout* check (whitespace, line wrapping). A file can pass clippy and fail `cargo fmt --check` simultaneously. bacon's default jobs run check + clippy + test but not fmt — adding a `fmt` job to `bacon.toml` closes the gap. Three-layer prevention is a reasonable maximum: (1) IDE format-on-save catches at edit time, (2) bacon's `fmt` job catches at file-save time, (3) `.githooks/pre-commit` catches at commit time. CI then catches anything that slipped past all three. | Evidence: empirical 050426 — M1-polish commit landed clean locally (clippy passed) but CI fmt step failed; rustfmt's max_width=100 wanted compact `assert_eq!` calls that local editor had wrapped multi-line. | Status: PROMOTED 050426.

- [050426] /wrap-up: **Generic-trait contract test pattern: `pub(crate) mod contract` with macro-generated wrappers per impl.** When a trait will have multiple implementations that must satisfy the same behavioral contract, structure tests as: (1) generic `pub(crate) mod contract` containing `pub fn foo<S: Trait>(s: &mut S)` test functions, (2) per-impl `mod impl_name_contract_tests` with a small `macro_rules! delegate!` macro generating thin `#[test]` wrappers that create a fresh impl and call the contract fn. New impls inherit all contract tests by adding one wrapper module — no test rewrites. Idiomatic in Rust where `cargo test` requires each test to be a `#[test] fn`; the macro avoids the per-test boilerplate. | Evidence: agent inference 050426 — applied to `Storage` trait per ADR 0006 point D; M3's `WalBackedStorage` will inherit 22 contract tests with one wrapper module. | Status: PROMOTED 050426.

- [050426 EOD] /wrap-up: **Rust 2018+ module convention: `src/foo.rs` + `src/foo/{submodule}.rs`, not `src/foo/mod.rs`.** Both styles compile and behave identically. The 2018+ flat-file form (sibling `.rs` next to a directory of submodules) is the modern convention; `mod.rs` is the older 2015-edition style and is now considered legacy in new code. Rust-Analyzer and rustfmt have no preference; Cargo errors only when *both* exist for the same module ("file for module `foo` found at both 'src/foo.rs' and 'src/foo/mod.rs'"). | Evidence: empirical 050426 — I scaffolded `src/server/mod.rs`; user instinctively created `src/server.rs` instead; then accidentally had both, hit the duplicate-module error. The 2018+ form was the right call from the start. | Status: PENDING.

- [050426 EOD] /wrap-up: **`usize::to_be_bytes()` is platform-dependent length** — returns `[u8; 4]` on 32-bit and `[u8; 8]` on 64-bit. Same trap exists for `usize::to_le_bytes()`. When serializing to a wire format that expects exact byte count (4 bytes for a u32 length prefix, 8 bytes for a u64 timestamp, etc.), always cast to a fixed-width type *before* `to_be_bytes()`: `(value as u32).to_be_bytes()` or `u32::try_from(value)?.to_be_bytes()`. Never rely on `usize` directly. | Evidence: empirical 050426 — `oversize_decode` test wrote `MAX_FRAME_SIZE.to_be_bytes()` (8 bytes on 64-bit) when the wire format expects 4. The decoder read first 4 bytes as `0x00000000`, returned an empty frame, and the test passed for the wrong reason. | Status: PENDING.

- [050426 EOD] /wrap-up: **Green-but-wrong test: input reinterpretation pattern.** A test passing doesn't mean it's testing what its name says. When the input got reinterpreted (wrong type width, wrong endianness, wrong length, wrong cast), the assertion can still fire on the *reinterpreted* data and look correct. Defenses: (1) read every test against its declared invariant, not the assertion alone; (2) when a test setup involves type coercion or byte-level construction, mentally trace what bytes/values actually result; (3) ensure each test exercises one variant of one behavior — mixing a "decode oversize" probe with an "encode oversize" probe in one body hides the bug because either passing makes the test green. | Evidence: empirical 050426 — the original `oversize_encode_decode_returns_error` test had a buffer-construction bug (see `usize::to_be_bytes()` nomination) and combined two unrelated assertions; the encode half passed, the decode half tested empty-frame decoding (inadvertently), and the test name lied. Caught in code review. | Status: PENDING.

- [050426 EOD] /wrap-up: **Surface alternatives for foundational deps before scaffolding code that uses them.** When introducing a foundational dependency (async runtime, framework, schema-driven serializer, ORM), surface alternatives explicitly *before* writing dependent code, even when the answer is "obvious." The discussion sharpens the rationale and creates an audit trail. The "we already decided this" assumption — even when accurate per a prior milestone-arc lock — leaves no record of *why* it was chosen, making future revisits harder. | Evidence: agent inference 050426 + user override 050426 — I scaffolded Cargo.toml with tokio without an alternatives discussion; user caught it ("Are we not gonna discuss the tokio dependency and alternatives?"). The follow-up discussion (vs. async-std, smol, glommio, sync threads) clarified the *why* even though tokio remained the choice. | Status: PENDING.

- [050426 EOD] /wrap-up: **Tuple struct vs named-field struct: rubric for newtype wrappers.** Tuple struct (`Frame(Vec<u8>)`) shines when (a) the wrapper IS its inner type (true newtype: `Bytes(Vec<u8>)`) or (b) positional ordering is canonical (`Point(f64, f64)`). For wrappers carrying semantically-distinct content that may grow fields later, prefer named struct (`Frame { payload: Vec<u8> }`) — `item.payload.len()` is self-documenting where `item.0.len()` requires looking up the definition. Future-proofs additive changes: at M4 we'll add `frame_type: u8`; named-field syntax handles this without renumbering. | Evidence: user feedback 050426 — pushed back on `item.0.len()` in scaffolded codec ("looks hard to read"). Refactored `Frame(Vec<u8>)` → `Frame { payload: Vec<u8> }` before tests landed. | Status: PENDING. Note: extends existing knowledge-base.md entry on enum-variant-shape rubric to struct-shape rubric.

- [050626] /wrap-up: **`std::sync::MutexGuard` is `!Send` — the compiler enforces "no lock across `.await`" automatically.** When `tokio::spawn` requires a `Send` future (default multi-thread runtime), and the future's state machine stores any locals alive across an `.await` point, holding a `std::sync::MutexGuard` across that point makes the future `!Send` and the spawn refuses to compile. This converts the chapter-3 footgun from a runtime mystery into a build error. Idiom: acquire the lock in a *block scope* so the guard drops before any `.await`. Use `tokio::sync::Mutex` only when you must hold the lock across an await (rare; pays an async-machinery cost). Paired with kintoun's design: storage critical sections are sync HashMap ops, never need to span an await. | Evidence: empirical 050626 — applied as the M2 connection.rs lock pattern; 7 duplex tests prove the rule mechanically (compiler accepts the block-scoped form, would refuse if guard escaped the block). | Status: PROMOTED 050626.

- [050626] /wrap-up: **Async server-test pattern: spawn the server task, drive the client side concurrently — never `.await` the server inline.** When testing an async server function via `tokio::io::duplex` or sockets, the server must run concurrently with the client driver. `tokio::spawn(server_fn(server_io, ...))` then drive the client side from the test body. If you `.await` the server function inline on the test task, the client side never gets to run and the test deadlocks. Bind the JoinHandle as `_server` if you don't need to assert shutdown, or keep it for an end-of-test `.await` that asserts `Ok`. | Evidence: empirical 050626 — first M2 connection test hung on `server.await.unwrap()` immediately after spawn because the client side was never driven. User saw bacon hang on save. | Status: PROMOTED 050626.

- [050626] /wrap-up: **Two-layer `JoinHandle` peel for tests asserting task success.** When the spawned future is `async fn() -> Result<T, E>`, awaiting the JoinHandle yields `Result<Result<T, E>, JoinError>`. The outer is "did the task panic or get cancelled?"; the inner is "what did the function return?". `result.is_ok()` only checks the outer layer — a function returning `Err(...)` produces `Ok(Err(...))` which silently passes `is_ok()`. Idiom: `let inner = handle.await.expect("task panicked"); assert!(inner.is_ok(), "function returned: {inner:?}");` — separate panic message per layer + `{:?}` diagnostic in the assertion message. | Evidence: empirical 050626 — caught in code review of `clean_eof_completes_with_ok`; user's first version asserted `result.is_ok()` on the outer Result only, so a buggy `handle_connection` returning `Err` would have passed silently. | Status: PROMOTED 050626.

- [050626] /wrap-up: **Pull sync helpers out of async functions to keep the await/lock-discipline boundary visible.** When an async function has a sync subsequence (no `.await` inside), extracting it to a sync helper makes the await boundary explicit at a glance. Reviewers can immediately see what holds locks vs. what suspends. In M2 connection.rs, `process_line(line, storage) -> String` is sync — parse → lock → execute → format — with no await; `handle_connection` keeps the awaits at the top level around frame I/O. The split documents that the lock cannot be held across an await without needing to read the whole loop body. | Evidence: agent inference 050626 — applied in M2 connection.rs scaffold; user accepted the structure unchanged; 7 tests pass. | Status: PROMOTED 050626.

- [050626] /wrap-up: **`std::prelude::v1::Result` in source code is rust-analyzer's "Insert explicit type" auto-fill smell.** When reviewing a `let` binding with a path like `tokio::task::JoinHandle<std::prelude::v1::Result<T, E>>`, that's IDE-generated. No human writes that path — `Result<T, E>` from the standard prelude is enough, and on `tokio::spawn` calls inference fills the whole type without any annotation. Code-review heuristic: spotting that path is a one-line cleanup signal. | Evidence: empirical 050626 — surfaced twice during M2 connection test review; user removed both occurrences. | Status: PROMOTED 050626.

- [050626 PM] /wrap-up: **`tokio::task::JoinSet` + `join_next().await` until empty is the canonical graceful-drain idiom.** When an async server needs to "stop accepting, then wait for in-flight work to finish naturally," spawn each per-task into a `JoinSet<Result<...>>` instead of bare `tokio::spawn`. On shutdown: drop the listener (release the port immediately), then `while tasks.join_next().await.is_some() {}` until the set drains. Per-task results can be inspected by binding the `Some(_)` value if needed; for "fire-and-forget swallow" they're discarded. Critically: a bare `tokio::spawn` with discarded JoinHandle gets aborted on runtime shutdown — the connection's response in flight is severed. JoinSet drain waits for natural completion. | Evidence: empirical 050626 — applied as M2 close shape in `serve()`; smoke-tested with real TCP client + SIGINT; clean exit code 0. | Status: PROMOTED 050626.

- [050626 PM] /wrap-up: **`tokio::pin!` + `tokio::select!` + `&mut shutdown` for cancellable async loops.** When a function takes a generic future as a "cancel signal" parameter (`F: Future<Output = ()>`), `F` isn't `Unpin` in general so it can't be polled directly. Idiom: `tokio::pin!(shutdown);` at function entry pins it on the stack, then `select!` arms can poll `&mut shutdown` repeatedly without consuming it. Without the pin, the borrow checker rejects the repeated poll. The other `select!` arm runs the loop's primary work (`listener.accept()` here); whichever future is ready first wins, the other's in-flight poll is dropped (cancelled, harmless). | Evidence: empirical 050626 — M2 `serve()` accept-or-shutdown loop; `&mut shutdown` after `pin!` was the load-bearing piece that made the `select!` compile. | Status: PROMOTED 050626.

- [050626 PM] /wrap-up: **Lazy tokio runtime: `Builder::new_multi_thread().enable_all().build()` + `runtime.block_on(async {...})` when only one branch needs async.** When `fn main` dispatches between sync and async code paths, don't make the whole binary async with `#[tokio::main]` — the sync branch then runs inside an unused runtime (KBs of overhead, no parallel benefit). Instead, keep `fn main()` sync, parse args first, then build the runtime only on the async branch. This matches the principle "async earns its keep where concurrency exists" — the REPL stays runtime-free, the server gets the multi-thread runtime, neither pays for the other's machinery. The `enable_all()` call turns on the I/O driver and time driver (signal::ctrl_c needs both — without it the future hangs forever). | Evidence: empirical 050626 — M2 main.rs dispatch; REPL branch unchanged from M1's sync 5-line shim; server branch builds runtime in `run_server(addr)`. | Status: PROMOTED 050626.

- [050626 PM] /wrap-up: **Borrow-checker quirk: hoist `drop(x)` after a loop rather than inside a `break` arm.** The compiler doesn't always reason that `break` precludes further iterations of the loop, so `drop(x)` inside a shutdown arm can produce a false "use of moved value" on subsequent iterations of `x` (e.g. `listener.accept()`). Hoisting `drop(x)` to immediately after the loop is functionally identical (the loop has already exited; no further accept) and keeps the borrow checker satisfied. General heuristic: when a borrow checker error appears within a `select!`/`break` pattern, try moving the `drop`/move-out to the post-loop position before adding lifetime annotations or restructuring. | Evidence: empirical 050626 — user hit exactly this during `serve()` impl; tried `drop(listener); break;` inside the shutdown arm, got a false-positive moved-value error on the next loop iteration's `listener.accept()`. Hoisting solved it. | Status: PROMOTED 050626.

- [050626 PM] /wrap-up: **`std::future::pending::<()>()` as a "never resolves" shutdown placeholder for tests.** When a function takes `shutdown: F: Future<Output = ()>` to support graceful cancellation, test rigs that want "serve forever" behavior can pass `std::future::pending::<()>()` — a future that yields once then never resolves. The turbofish `::<()>` pins the output type so `F`'s `Output = ()` bound is satisfied at the call site (without it, type inference fails because nothing else constrains the unit type). Production callers pass real shutdown signals (`tokio::signal::ctrl_c()` wrapped). One signature serves both. | Evidence: empirical 050626 — `tests/tcp_integration.rs::spawn_server` uses `pending::<()>()` so the existing 6 integration tests work unchanged after `serve()` gained the shutdown parameter. | Status: PROMOTED 050626.

- [050626 PM] /wrap-up: **`F: Send` is required only when futures cross thread boundaries — not for in-place `select!` polling on the same task.** A common over-bound: putting `F: Send` on every generic future parameter "because multi-thread runtime." Wrong. `runtime.block_on(future)` runs `future` on the calling thread for the entire `block_on` lifetime; tasks spawned *inside* that future via `tokio::spawn`/`JoinSet::spawn` need `Send + 'static` because they migrate to worker threads, but the outer `block_on` future and any futures it polls in-place via `tokio::pin!` + `select!` stay put. Add `F: Send` only when `F` is explicitly spawned/moved to another task; otherwise omit it. | Evidence: empirical 050626 — original `serve()` doc claimed `F: Send` was needed; the actual bounds didn't include it (and didn't need to); user asked "Does that mean the implementation does not work on multi thread systems?" The answer was: no, it works fine, the doc was over-strict. Fixed the doc. | Status: PROMOTED 050626.

- [050626 PM] /wrap-up auditor T1: **Doc claims about generic bounds must match the actual `where` clause.** Over-strict doc bounds are silent until a user asks — failure mode is subtle (doc says `F: Send`, code doesn't require it, user gets confused about runtime behavior) and not obvious from reading code in isolation. Pre-commit check: read the doc comment alongside the actual generic-parameter bounds; reconcile. | Evidence: agent inference 050626 + auditor T1 verdict 050626 — caught by user question on `serve()` doc claim that `F: Send` was needed for multi-thread runtimes; bounds had no Send because shutdown future stays pinned on serve task's stack. Doc fixed. Destined for "Code Review Heuristics" section. | Status: PENDING — promote on next audit cycle per auditor verdict.
